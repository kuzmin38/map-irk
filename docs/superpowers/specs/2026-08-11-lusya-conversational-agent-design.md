# Люся: разговорный агент для чтения информации (личка)

Дата: 2026-08-11
Статус: одобрено, готово к написанию implementation-плана

## Зачем

Сейчас Люся отвечает на свободный текст только по жёстким паттернам (адрес дома,
запрос вида «адрес кв N» для стояков). Всё остальное — через кнопки меню.
Андрей хочет, чтобы на вопрос в свободной форме («где стояк по такой-то квартире»,
«что с заявкой на Байкальской 99» и т.п.) Люся отвечала сразу, без блуждания
по меню, живым тоном с лёгкой иронией — а не сухим «ничего не нашла».

Это первый шаг в более крупном плане (мониторинг общего рабочего чата
«Обслуживание», см. «Вне рамок»), но обкатываем сначала один на один.

## Рамки

**В рамках v1:**
- Свободный текст только для **чтения** данных: дома, паспорта, документы
  (список), стояки, справочник/нормативы, статус заявок, работы/дедлайны.
- Личные диалоги (1:1), не групповой чат.
- Долгосрочная память в уже существующей SQLite-базе (`bot.db` на volume
  Railway) — без похода во внешние системы.

**Явно вне рамок v1** (следующие проекты):
- Создание/редактирование данных через свободный текст (заявки, паспорт,
  показания счётчиков, работы) — остаются пошаговыми диалогами через кнопки,
  как сейчас. Форма для точного ввода данных лучше свободного текста.
- Мониторинг группового чата «Обслуживание» и автономные реплики там
  (проект B) — использует то же ядро агента, но добавляет отдельный слой
  «когда встревать» и связанные риски публичного поведения на глазах
  руководства. Делается отдельным заходом после обкатки v1.
- Интеграция с Obsidian-хранилищем (`G:\Мой диск\Память AI`) как общей базой
  знаний с Евой, перенос туда паспортов/документов домов, техдокументации.
  Требует моста к Google Drive (авторизация, синхронизация) — отдельный
  инфраструктурный проект (C). Причина отложить: Railway-контейнер не имеет
  прямого доступа к `G:\` диску пользователя.

## Архитектура

Новый модуль `bot/agent.py` — агентный tool-calling слой поверх `bot/ai.py`
(уже переведён на OpenRouter). Встраивается **последним шагом** в `on_text`
(`bot/handlers.py`), после того как отработали и не дали ответа все
существующие быстрые пути по порядку:

1. активный пошаговый диалог (`STATE`)
2. парсер стояков (`risers_mod.parse_query` + `locate`)
3. поиск дома по адресу (`houses.search`)
4. **агент** (новое) — если ничего из вышеперечисленного не сработало

Ничего из уже работающего не трогаем — агент это тихий fallback.

### Модель

`OPENROUTER_MODEL` переключается с бесплатной `moonshotai/kimi-k2:free` на
платную `moonshotai/kimi-k2` (тот же ключ, тот же API OpenRouter). Причина:
нужен стабильный tool calling, бесплатный тариф может капризничать перед
презентацией начальству.

### Цикл агента

Стандартный tool-calling loop:

1. Собрать сообщения: системный промпт (характер + описание инструментов)
   + профиль пользователя из `user_notes` + последние ~6 реплик диалога
   из `chat_history` + новый вопрос.
2. Отправить в Kimi K2 со списком инструментов (OpenAI tools-формат,
   аналогично `tools_to_openai` в `ai-assistant-bot/src/ai/llm.py`).
3. Если модель просит вызвать инструмент — выполнить его синхронным Python-
   кодом по локальным данным, результат вернуть в диалог, повторить.
   Максимум 4 круга — защита от зацикливания.
4. Финальный текстовый ответ — пользователю. Записать обмен (вопрос + ответ)
   в `chat_history`.

### Инструменты агента (read-only)

- `find_house(query)` — обёртка над `houses.search`
- `get_passport(house_id)` — `db.get_passport`
- `list_docs(house_id)` — `db.list_docs` (только список названий/примечаний,
  не содержимое файлов)
- `get_riser(address, flat)` — обёртка над `risers_mod.locate`
- `get_directory(section)` — `directory.json` (нормативы, телефоны)
- `get_house_works(house_id)` — `db.list_works`
- `get_open_requests(house_id=None)` — `db.list_requests`

## Долгосрочная память (в bot.db, без Obsidian)

Две новые таблицы в `bot/db.py`:

```sql
CREATE TABLE user_notes (
    user_id INTEGER PRIMARY KEY,
    profile TEXT NOT NULL DEFAULT '',
    updated_at TEXT NOT NULL
);

CREATE TABLE chat_history (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL,
    role TEXT NOT NULL,       -- 'user' | 'assistant'
    content TEXT NOT NULL,
    created_at TEXT NOT NULL
);
```

- `chat_history`: последние ~6 реплик на пользователя подгружаются в контекст
  каждого запроса к агенту. Старые строки не обязательно удалять сразу —
  достаточно ограничивать выборку `ORDER BY id DESC LIMIT 6` при чтении;
  подчистка совсем старых записей — не приоритет v1.
- `user_notes`: после диалога (или раз в несколько сообщений) агент отдельным
  вызовом ИИ обновляет выжимку — устойчивые факты о пользователе (привычки,
  к каким домам чаще обращается, как формулирует вопросы). Профиль
  подгружается в системный промпт при следующем разговоре — Люся не
  начинает с чистого листа.
- Обе таблицы живут на volume Railway (`BOT_DB=/data/bot.db`) — переживают
  передеплой.

## Характер

Системный промпт получает уточнение тона: своя, с лёгкой иронией, может
подтрунить, вставить шутку про течку или аварийку, но остаётся полезной и
точной по делу. Обращение на «ты» по имени.

## Обработка ошибок

Если `OPENROUTER_API_KEY` не задан, модель недоступна, таймаут или исчерпан
лимит циклов инструментов — откат к нынешнему поведению: «🤷‍♀️ По запросу
«...» я ничего не нашла» с кнопкой меню. Пользователь не должен увидеть
голый traceback или зависание бота.

## Тестирование

Тестов в проекте пока нет, добавляются точечно:

- Юнит-тесты на инструменты агента (`find_house`, `get_passport`,
  `get_riser` и т.д.) — чистые обёртки, тестируются без сети и без ИИ.
- Тест на диспетчер инструментов — фейковый ответ модели с `tool_calls`,
  проверка, что вызывается нужная функция с нужными аргументами
  (HTTP-вызов к OpenRouter мокается).
- Ручная проверка качества понимания вопросов — на реальных диалогах с
  Андреем, до показа начальству. Автотестом не покрывается.
